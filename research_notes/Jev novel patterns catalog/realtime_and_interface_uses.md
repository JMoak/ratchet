# Real-time, embodied and interface uses of Jev (15 Sep - 16 Oct 2026)

Scope: uses where a Jev-class decision model (TypeSafe's hosted Jev 1.13/1.14, or an open re-creation of its API) sits inside a control loop as a reflex or sensor, rather than as a judge in a pipeline. Capture date for every URL below is **2026-10-16** unless marked "(captured 2026-10-15 by the earlier researcher)". Labels: **[official]** = TypeSafe or a vendor describing its own system; **[independent-with-code]** = third party with a public repo and reported numbers; **[anecdotal]** = social post, demo page or press quote without code or method.

Background needed to read the numbers: Jev exposes Noul (P(true)), Choice (2-255 options, distribution + confidence) and Score (2-10 levels); all questions in a request share one `state` and are evaluated in parallel; input is $0.042/M tokens and output is free; the default context is 64k per request / 32k per question — [TypeSafe models page](https://docs.typesafe.ai/models); [opentweet limits summary](https://opentweet.io/jev/limits). Jev 1.14 (14 Oct 2026) adds an experimental fourth answer type, **Box**, behind a `TypeSafe-Danger-Zone-Images: true` header — [TypeSafe Box docs](https://docs.typesafe.ai/go/box).

## KQ1. Games and simulation: what did Jev decide versus a planner, and at what frequency?

### Takeaway
Every working game loop splits control three ways: code runs reflexes at engine rate (20-500 Hz), Jev picks one option from a bounded, code-filtered menu at 1-10 Hz (one Choice plus a few speculative Nouls/Scores per request, ~500-4,000 input tokens), and a generative planner, if present, runs only at milestones. Measured hosted-Jev decision latency in these loops clusters at 110-380 ms median; the only sub-30 ms figure (Hao AI Lab) is a self-served open model on Blackwell, not hosted Jev. Where a scripted baseline exists it usually matches or beats Jev (pick-and-place, RuneScape, NetHack, grid steering); Jev's measured edge is over generative LLMs on cost and loop rate, not over code.

### Inferences
- The frequency ceiling for hosted Jev in a game loop is set by round-trip latency, not throughput: every hosted loop that reports a median (211-380 ms at 500-4,000 tokens) runs at 1-4 Hz sequentially and reaches 6-10 Hz only by overlapping requests (pong-jev concurrency 3, jev-drone 4-6 workers, TypeSafe's own 10 q/s Doom). The 24 ms MCJev number is an open model colocated with the game server, and even there the first tunnelled setup was 330 ms.
- "What Jev decided vs the planner" is consistent across Minecraft, Doom, RuneScape and Pokémon: the planner (Astra/Hermes/Claude/human-written goal list) sets objectives at milestones; Jev picks one of 3-20 pre-validated options per tick; code owns validity, pathfinding, aiming and all arithmetic. Several authors concede the harness carries the game knowledge (jevscape, Pokémon HN, hbrn's coin-flip remark), and three scripted baselines matched or beat Jev (jevscape random 235 vs 197 peak XP/min; NetHack first-option baseline reaching the same Dlvl 11; pick-and-place rules identical to Jev).
- The cheapest reliability wins came from shrinking the menu, not improving the model: withholding `mine_dirt` and `wait` (teknium1), non-overlapping option names and percentage-named levels (grand-prix), digit-free relative phrases (pong-jev), banded HP/distance (jev-state 74% -> 100%).

### Gaps
- No controlled win-rate comparison of hosted Jev vs an LLM or scripted bot on Doom; TypeSafe says only that a non-AI bot would be better, and the Register's "tied a mid-tier, lost to the best" line from the earlier notes could not be re-verified in the fetched article.
- Hao AI Lab publishes no p95 latency, no dollar cost and no fallback-when-late behaviour; the 70% Block UHC win rate is against self-selected public players with no skill control.
- The ViZDoom 5 Hz / 12 Hz agent, the Jev Arcade 9 Hz FPS and the 96%-agreement MMORPG mapper exist only as X posts (mirrors returned 404); no code or method was reachable.
- Ronak Malde's original repository was not located; only ASCII.jp's description and teknium1's reproduction are available.
- No crafting-decision loop with numbers was found; Minecraft uses are combat (Hao, Vipul) and navigation/milestone action selection (Malde, teknium1, souta-lab).

## KQ2. Robotics and drones: sensors to text, rates, safety floors, failures

### Takeaway
All embodied Jev uses found are simulations (MuJoCo, Three.js, LIBERO); none report real hardware. The pattern is a 50-500 Hz geometric controller, a 15-50 Hz perception/reflex layer that is the real safety floor, and Jev as an advisory tactical layer at 2-5 Hz fed a JSON scene (range sectors, poses, contact flags), with code refusing manoeuvres that violate measured limits. In the only study with a rules baseline, Jev "chose exactly the same action sequence as the rules controller in all 20 episodes"; in the richest drone project the headline run hit a sim-time bug where "152 of 182 requests hit a full queue, so the model influenced nothing".

### Cited Findings
- `RomanSlack/jev-drone` (MuJoCo, Skydio X2 model, camera only): classical CV turns depth/segmentation into "five forward range sectors, the height of the blocking obstruction, whether its top edge is visible, and the target's position" as JSON. Rates: 500 Hz geometric controller, 50 Hz guidance/safety reflex, 15 Hz camera-to-scene, ~2.5-3 Hz Jev "advisory only". One call returns `maneuver` (Choice: hold_course, gap_left, gap_right, climb, brake, reacquire), `risk` (Score) and `target_truly_lost` (Noul). Code skips the call on an open corridor with target in view and "reuses the last judgment when the scene fingerprint is unchanged". Safety: the 50 Hz reflex overrides when something is close; code refuses `climb` unless the measured top edge is within the climb ceiling; reflex brakes only for middle-sector obstacles; vertical acceleration clamped positive. Latency: 0.11 s median engaged, tunnel 0.118 s median / 0.164 s p90; sequential ceiling 7.4 Hz; pipelined 4-6 workers 21 decisions/s, zero errors in ~2,000 calls. Budget at 9 m/s: perception 0.03 s, Jev 0.118 s, decision age 0.024 s, airframe 0.70 s ("The model is 13% of the loop; the vehicle is 80%"). Single 65 s run: furthest point 17.7 m baseline vs 77.5 m Jev, target in view 19% vs 82%, time pinned in reflex 65-71% vs 9%, 0 collisions both; 80 calls, 96k tokens. Caveats: one run, an earlier arena showed no advantage over 3 seeds, hand-built scenes 6/7 correct; "Early on, Jev never chose `climb` because the state had no vertical information"; in the tunnel it "tends to over-commit and hit a wall"; the pacing bug left 152/182 requests queued — [GitHub](https://github.com/RomanSlack/jev-drone)
- `khordoo/jev-reflex-autonomy-lab` (the "15 drones" swarm): 1-15 drones, each with Jev as "System 1 reflex layer"; System 2 "is consulted only when confidence falls below the configured threshold" and "does not fly the drone directly, and Jev does not pause while waiting for it"; collided drones are removed and the rest continue; one successful 15-drone run: 201 decisions, ~5.65M tokens, ~$0.24 (~$0.0012/decision, i.e. ~28k tokens per decision); runs are non-deterministic because "provider latency can still change trajectories"; "an experimental visualization, not a production flight controller"; no tick rate, state schema or safety floors described — [GitHub](https://github.com/khordoo/jev-reflex-autonomy-lab). The original post: "Decision latency: < 300ms ... Survival rate: 100% (all 15 reached the destination)" [anecdotal] — [eChai mirror of @MKhordoo](https://echai.ventures/feed/jev-can-control-a-swarm-of-15-autonomous-drones-in-real-time-i-built-615)
- `jev-autopilot` (Three.js city, pad A to pad B): code computes altitude, bearing, speed, obstacles ahead and tallest building into a plain-language report; six questions per request (Choice per stick axis: throttle, yaw, pitch, roll; Booleans: commit to landing, cut motors); axes are set "from the probability distribution of Jev's answer"; "a few hard safety limits kept in code" (unlisted); ~200 ms per answer; "A trip costs $0.01"; no success rate — [GitHub](https://github.com/arielweinberger/jev-autopilot)
- `jev-pick-and-place-study` (MuJoCo Fetch, 500 Hz physics): one bounded command every 0.2 simulated seconds; state is exact positions, contact/alignment flags and explicit rules; 10 seeds x {normal, target change} = 20 episodes per controller, 100-decision limit. Reactive rules 10/10 and 10/10, <0.01 ms, $0; Jev 1.13.0 10/10 and 10/10, median 146 ms, $0.0035 per success ($0.0695 total); Claude Haiku 4.5 4/10 and 1/10, 732 ms, $0.4174 per success ($2.087 total). "Jev chose exactly the same action sequence as the rules controller in all 20 episodes"; simulation pauses during API calls — [GitHub](https://github.com/tryaksh/jev-pick-and-place-study)
- `RoboJEV` (Franka Panda, MuJoCo): two-stage per decision (intent, then X/Y/Z `negative/zero/positive` + gripper `open/hold/close`), "at least two API requests" per decision; 1 cm steps, 4 mm within 25 mm of the socket; 2 ms physics; "malformed or inconsistent responses execute no action" is the only stated safeguard; 10 seeds per task: pick&place 10/10, push 10/10, stack 8/10, loose peg 10/10, gate pick&place 5/10 (rule baseline 8/10); failures: arm-link collisions, "repeated wrong-direction requests exhausting the decision budget", two validation failures; 113 transport errors (all recovered) and 38 HTTP 402 account blocks; adding full geometry did not help (3/10 vs 2/10; double-gate 0/10 both) — [GitHub](https://github.com/lykycy123/RoboJEV)
- `jev-libero` (LIBERO manipulation): three layered Choices per decision (intent, contact/motion family, one of 27 atomic inputs) with reversible physics previews of each candidate for up to 8 env steps / 0.4 s; ~7.9 env steps per decision; model cost per task $0.0012-0.0030; one passing recording per task, no success rates or latency — [GitHub](https://github.com/Dimweaker/jev-libero)
- Catalogue-only robotics entries: `embodied-jev` (MuJoCo workbench with MiniCPM5-2B and Jev), `Multi-UAV-JEV` (UAV pursuit), `jev-askable-arm`, `JEV_control_your_roboarm`, `JEVsees` ("Real-time visual decisions from RGB, video, and RGB-D cameras; no figures"), `lus222-jev-challenge` (FPV, three pilots) — [awesome-jev README](https://raw.githubusercontent.com/hellogumbo/awesome-jev/main/README.md)
- A negative practitioner verdict: Jev is "fine as an async harness, but not as a 5 Hz control loop" [anecdotal, LinkedIn] — [Ozkan Ceylan](https://de.linkedin.com/in/ozkanceylann)

### Inferences
- Safety floors in these projects are never Jev thresholds alone; they are code that (a) withholds options Jev may not choose (climb ceiling, legal moves), (b) runs a faster reflex that overrides Jev (50 Hz brake), and (c) executes nothing on malformed answers. This matches the ratchet invariant "floors can only raise caution".
- The jev-drone budget breakdown (model 13%, airframe 80%) and the pick-and-place result (identical to rules) together suggest the embodied value of Jev is semantic flexibility of the state description, not reaction time; where the task is fully specified by geometry, a rule does the same thing for free.
- Cost per decision in embodied loops spans 200x (pong ~520 tokens vs khordoo ~28k tokens) purely from state verbosity; the drone-swarm cost is dominated by prompt size, not call count.

### Gaps
- No real-hardware deployment (ROS, Raspberry Pi, physical drone or arm) was found; a targeted search returned nothing Jev-specific.
- No failure report from a physical system exists; the only crash-class failures are simulated (tunnel over-commit, arm-link collisions).
- khordoo's repo does not state the per-drone state, tick rate or the <300 ms measurement method behind the 15-drone post.

## KQ3. Browser and GUI agents: speculative heads, element tables, LLM handoff, measured gains

### Takeaway
The dominant design is one request per step containing an operation Choice plus speculative target Choices (one per operation type, each restricted to compatible elements), over a numbered table of visible controls (role, name, value) with no screenshot; code executes only the head matching the chosen operation and re-checks freshness/occlusion before input. A small text LLM is called only when a field needs a value. Measured gains are architectural: browser-use's 1,092 -> 101 protocol calls and 9.45 -> 7.09 s median task time; per-decision latencies of 82-460 ms vs 4-5 s for a screenshot LLM; $0.0002-0.001 per step. Task-success benchmarks are nearly absent; JevForge's Mind2Web element top-1 (Jev-1.13 0.543 test / 0.610 OOD) is the only one.

### Cited Findings
- `browser-use/jev-ultrafast` [independent-with-code]: `snapshot.js` reads visible controls into a numbered element table (index, role, name/value) keeping DOM node references; operations CLICK, TYPE_TEXT, SELECT, SCROLL_UP/DOWN, WAIT, DONE, BLOCKED; heads `click_target`, `type_text_target`, `select_target` each hold only compatible elements; "Target questions are speculative"; "Two decisions, one network round trip"; "Model output never becomes selectors, coordinates, shell commands, or executable JavaScript". Only TYPE_TEXT triggers the text LLM (`inception/mercury-2.5`, reasoning off) and its output "must parse as a small JSON object before typing"; a generated value survives a stale-page retry only if the whole helper input is unchanged. Clicks re-check document, form values, target and nearby context; "Animation alone does not force another prediction"; executor rejects covered controls; after typing into a combobox it waits up to 200 ms for suggestions, otherwise at most two animation frames or 50 ms. Google Flights 7,073 ms; six alternating runs: median 9.450 s -> 7.092 s, protocol calls 1,092 -> 101; Wikipedia 2.798 s; hotel search 1.896 s; "not a general reliability benchmark"; "A `DONE` choice still requires independent outcome verification"; out of scope: shadow roots, frames, canvas, uploads, pop-up tabs, nested scrolling. No low-confidence fallback and no option shuffling documented — [GitHub](https://github.com/browser-use/jev-ultrafast). Per-run cost $0.0039 (captured 2026-10-15 by the earlier researcher) — [Inside.com.tw](https://www.inside.com.tw/article/42431-jev-ultrafast-browser-agent-gregpr07)
- `ego-jev-ultrafast` (same pattern, multi-model helper benchmark) [independent-with-code]: median decision step 0.6-1.9 s; HN-comments click task ~2.5 s end to end; Google Flights 10 steps ~60 s "mostly page animation and the helper model"; freshness guards compare a page fingerprint and re-check each element "connected, visible, enabled, not covered"; re-observe once if fewer than six actions remain after a click; observation after clicks capped at 300 ms; stop after 3 consecutive no-ops; budgets 60 actions / 120 model calls; "Unbookable future dates cause the agent to loop until the step budget stops it"; residual risks: a millisecond window between hit-test and CDP input, and "a DONE judgment made by the same model that acts" — [GitHub](https://github.com/shikaizhong-design/ego-jev-ultrafast)
- `jev-ui-test` [independent-with-code]: response rejected and resent unless the choice is a candidate ID, probabilities normalise and the selected option has the highest score (`validate_choice`); median 458 ms per operation decision, 30 of 32 under 1 s, p90 919 ms, vs "4-5 seconds, occasionally 10" for direct LLM driving (empirical, no machine-readable evidence); no back action; assertions only on the final page — [GitHub](https://github.com/buer2233/jev-ui-test)
- `JevForge` (Qwen3.5-0.8B trained to the Jev interface, Mind2Web) [independent-with-code]: candidates expand into K rows, the model pools the final token and normalises only the K logits ("avoids language-model decoding"). Choice top-1 test/OOD: raw Qwen 0.235/0.340, JevForge 0.8B 0.579/0.637, Jev-1.13 0.543/0.610; Noul acc/Brier test: JevForge 0.826/0.128, Jev-1.13 0.910/0.092; no step or task success, latency or cost — [GitHub](https://github.com/zwliJay/jev-forge)
- Stagehand/Browserbase [anecdotal]: Kyle Jeong (17 Sep): "observe the page, send a11y tree as state + actions as questions, Jev decides the next action, then Stagehand"; "this task cost $0.001"; "near instant speed (in a remote browser btw)"; no latency, success or code — [hermes-ai.net mirror](https://hermes-ai.net/en/jev/case/2100622054945095934/); [X](https://x.com/kylejeong/status/2100622054945095934). No Browserbase-official integration found in Browserbase or Stagehand docs — [Stagehand agent docs](https://docs.stagehand.dev/concepts/agent)
- `awlevin/typesafe-computer-use` (macOS) [independent-with-code]: Vision OCR on the frontmost window plus accessibility-tree labels; code adds parsed dates and offsets, repeated-label row, focused field, app/URL and actions already tried; one request answers three Choices (action kind, item, site); "the next capture is the only witness of what it did"; when the classifier stops, a writer model "reads the screen and answers ... It never picks an action". Per decision $0.0002 vs $0.032 (Opus 5, bare screenshot) "155x cheaper"; 12-step task $0.003 vs $0.40-0.90; model latency 0.13-0.38 s vs 5.2 s; end-to-end step ~1.5 s vs ~5.5 s ("3.7x"); input tokens 4,882 vs 4,785. "Every piece of reasoning the frontier model does for free has to be rebuilt here as deterministic state." OSWorld results referenced but not in README — [GitHub](https://github.com/awlevin/typesafe-computer-use)
- `dabit3/jev-experiments/jev-ax-pilot` (macOS accessibility-tree agent) [independent-with-code]: state is goal, step, app, window title, focused element, up to 14 lines visible text, up to 60 actionable elements (e1..eN), text candidates, previous actions and "code-evaluated arithmetic facts"; 5-6 questions per request (`next_element`, `key`, `goal_reached`, `needs_text_input`, `is_destructive`, `text` only when >1 candidate); Jev p50 82-126 ms, p95 138-351 ms; AX reads 37-350 ms per step; 0.6-0.8 steps/s with Jev "10-15% of a step"; simulated 3 s LLM mode 0.13 steps/s; $0.0002-0.0006 per run (1.9-2.1k input tokens/decision); five preset goals completed; one HTTP 429 handled by a deterministic heuristic; heuristic-only mode gets "stuck" on System Settings — [GitHub](https://github.com/dabit3/jev-experiments/tree/main/jev-ax-pilot)
- Milind S "computer use without screenshots" (17 Sep) [anecdotal]: local CoreML segments UI elements, on-device OCR reads labels, "That text is all Jev gets"; "~90ms per decision"; loop re-runs detection after each click; no cost, success or code — [madewithjev build page](https://madewithjev.com/builds/computer-use-without-screenshots)
- `droidrun/mobile-jev` (Android) [independent-with-code]: indexed controls and installed apps -> one Jev request where "Operation and compatible-target questions share one request"; ops OPEN_APP, TAP, TYPE_TEXT, scroll, navigate, WAIT, DONE, BLOCKED; optional `--confidence` cutoff; rejects stale targets; text is copied from goal spans so "A separate text-generation model is not needed"; demo "about 21 seconds for 9 actions"; "never retries a device mutation after an uncertain transport failure"; "Jev's DONE response is not independent proof of success" — [GitHub](https://github.com/droidrun/mobile-jev)
- Other per-step latencies claimed in the catalogue (READMEs not fetched): `hunch` ~150 ms clicks; `jev-mcp` ~100 ms; `CloakBrowser-Agent` ~0.3 s/step; `jev-ra` ~300 ms; `ego-jev` ~0.4 s per DOM step; `jev-browser-control` ~0.5 s; `omarchy-laser` "judges every screen, about 1 cent/day"; `jev-voice-browser` ~300 ms per spoken word — [awesome-jev README](https://raw.githubusercontent.com/hellogumbo/awesome-jev/main/README.md)
- TypeSafe's own position-bias note applies directly to element ranking: "`jev-1.13` leans toward the option that comes first ... reorder the options to double check that the answer stays consistent" — [TypeSafe jaggedness docs](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

### Inferences
- None of the fetched browser/GUI projects shuffles or rotates element order despite the documented first-option lean; since element tables are DOM-ordered, the bias systematically favours top-of-page controls. The only mitigation in use is structural (restricting each head to compatible elements), not statistical.
- "Measured protocol-call reductions" exist only for jev-ultrafast; the 10x drop comes from replacing screenshot+LLM round-trips with a single snapshot call plus one decision request, i.e. it would hold for any sub-second classifier.
- Handoff to a text model is universally one-directional and narrow: the LLM writes a string or an answer, never picks an action; two projects (mobile-jev, jev-ax-pilot) avoid the LLM entirely by letting Jev pick a span from the user's goal.

### Gaps
- No task-success rate on a standard benchmark (WebArena, OSWorld, AndroidWorld) for any hosted-Jev agent; awlevin references OSWorld docs that were not reachable, JevForge gives element top-1 only.
- No project reports how often Jev picks BLOCKED or falls below a confidence cutoff in practice, or what the operator does then.
- No measured regional or gateway latency split for browser agents; one README notes p50 "depends on distance to `api.typesafe.ai`" (see KQ6).

## KQ4. Interface generation: Jev picks the UI, forms, autocomplete, keystrokes, accessibility

### Takeaway
"Jev picks the UI" is implemented as Choice over a fixed component catalog (Workday Sana, Vercel json-render, Instinct's 48 shadcn components, CopilotKit panels) with code or an LLM filling data; Workday's "instantly" claim has no published number, while the comparable Very Good Ventures test cut median dashboard render from 29 s to 3.8 s by routing closed questions to Jev. Keystroke-rate uses (launcher, shell history, spreadsheet headers, IME reranking, voice drawing, voice turn-end) all share one mechanism: local results first, one Jev request per input change, cancel superseded requests, drop late answers, and gate on probability bands; measured p50 is ~100 ms at ~1.4k tokens and 300-900 ms at larger states.

### Cited Findings
**Component selection**
- Workday Sana [official/press, New Stack 13 Oct]: Sana "builds each screen as you type"; a paycheck card appeared before the presenter finished typing; Hellermark: "you just give it all of the design components to pick from"; Workday "hard-coded none of the selection logic" and "had to get data preloading right"; LLM-written UI is "quite slow", classification lets you "literally do it instantly"; design-system size not disclosed; no statement on what Sana does "when no combination of components fits". Very Good Ventures (Andrew King): closed questions to Jev, others to a frontier model; Jev answers below 50% confidence go to a language model ("a cage with a door"); median render 29 s -> 3.8 s on synthetic data; "A shape nobody anticipated cannot appear on screen." OpenRouter Banking77 (intent, not UI): Jev median 175 ms, 81% vs Claude Opus 5 84.4% at 2.3 s and ~22x cost. CopilotKit recipe: Jev picks which prebuilt panel to show with an OpenAI fallback. Vercel Labs testing a Jev mode in json-render — [The New Stack via reader proxy](https://r.jina.ai/https://thenewstack.io/workday-is-using-typesafes-jev-to-build-user-interfaces-on-the-fly/) (original: https://thenewstack.io/workday-is-using-typesafes-jev-to-build-user-interfaces-on-the-fly/)
- Vercel `json-render` Jev mode [official, experimental]: `experimental_createEvaluator` (tested model ID `typesafe-ai/jev`) + `experimental_composeSpec`; "Each candidate is a configured component instance"; "One evaluation selects the root and required components together, and immediately emits a validated preview", a second arranges them; default budget 32 evaluations, at most 32 elements, depth 8; default timeout 10 s per evaluation; "Jev cannot invent missing prose or data"; confidence "not a calibrated quality threshold" — [json-render Jev docs](https://json-render.dev/docs/jev); [GitHub](https://github.com/vercel-labs/json-render)
- `Quintui/json-renderer` [independent-with-code]: LLM mode (Claude Haiku 4.5 streams a spec), Jev mode ("New UIs take two evaluations and produce no output tokens"), hybrid (Jev picks layout, LLM fills copy, both start together; the LLM "cannot change component types, layout, actions, metric values, or identity fields"); no latency or quality numbers; hybrid's value "has not been established" — [GitHub](https://github.com/Quintui/json-renderer)
- `Instinct` [independent-with-code]: 48 shadcn components in 7 families (16 "deep") + 17 blocks; call 1 is speculative (Noul section-vs-component gate, 7-way family Choice, per-candidate-field relevance Score and type Choice, three style and three taste questions, block choices); call 2 picks within the top 2 families (beam width 2); call 3 only on thin margin; "parallel fan-out costs tokens, not latency"; no timings; duplicates can slip through; word banks ~5-6 entries — [GitHub](https://github.com/joevidev/ui-generator-instinct-jev)
- `design-os-generative-ui` claims "Sub-50ms Real-Time Generative UI" but the README has no benchmark, method or Jev selection logic — [GitHub](https://github.com/jangtrinh/design-os-generative-ui)
- Catalogue: `shapeshift` ("input morphs into the right UI"), `jev-ui` (React components choose what to render and order), `Jev Room` (six room settings), `typesafe-ui` (TypeSafe's shadcn-style components) — [awesome-jev README](https://raw.githubusercontent.com/hellogumbo/awesome-jev/main/README.md)

**Form/spreadsheet prediction**
- `judge-sheets` [independent-with-code]: after 120 ms without keystrokes one `choice` request sends the header plus three sample rows and Jev picks one of 14 schemas (chip shows e.g. "Urgency · 91% · 72 ms"); Enter fills `=JUDGE` (noul), `=PICK` (choice) or `=RATE` (score) formulas; all questions about one row go in one request; 12-lane pool (`JEV_CONCURRENCY`), NDJSON streaming, retries on 429/529/5xx, stalls aborted at 2.5 s; header chip 72-132 ms; per-request p50 114-120 ms, p95 259-379 ms (300 rows); 300-row column 3.5-5.2 s = 57-85 rows/s vs ~20 min for a 4 s/cell LLM ("230-339x"); answers cached by (kind, text, instructions, options) so re-trying a header makes zero requests; quality "checked by hand, not benchmarked" — [GitHub](https://github.com/dabit3/jev-experiments/tree/main/judge-sheets)

**Keystroke / autocomplete**
- `jev-launcher` (archived; moved to `dabit3/launcher`) [independent-with-code]: local fuzzy results appear immediately and "Jev's answer refines them when it arrives"; each query change starts one request (skipped in local-only mode or rate-limit cooldown); "Superseded requests are canceled, and late responses are rejected"; state is the query prefix plus `frontmost_app`, `recent_apps`, `clipboard_kind`, `time_of_day`, `weekday`, optional time window, and 13 candidates (30 with a time window; Spotlight capped at 150); questions in one round trip: `target` (Choice + `none`), `action` (10 types), `ready` (can Enter run the top row), `scope` (`one`/`all`), `match_cN` per candidate; `score = 0.65·P(target) + 0.20·P(action matches kind) + 0.15·fuzzy`; green Enter at `ready` >= 0.6 or one target >= 0.9; group row at P(all) >= 0.5; p50 ~100 ms, p95 ~200-300 ms, first request ~500 ms (TLS), 30-candidate set 160-330 ms at ~2.7k tokens; ~1,400 tokens/decision, ~$0.00006 per keystroke, five-query session ~$0.003; "Canceled requests may still be billed server-side"; 429/529 pause with `Retry-After`; thresholds "tuned by hand on a small set of queries" — [GitHub](https://github.com/dabit3/jev-experiments/tree/main/jev-launcher)
- `jev-shell-history` (zsh) [independent-with-code]: every buffer change kills the in-flight request and starts a new one; result applied only if "the buffer is still what was typed when the request started"; candidates = last 100 distinct history entries (prefix matches only if any exist); two questions per request (Choice over IDs, Noul "does any candidate complete the input"); fuzzy suggestion only if top score >= 0.3 and (Noul >= 0.5 or top >= 0.9) because "the two signals fail in different places"; "roughly 0.7-0.9 s per request, almost all of it API time"; no debounce, no cache — [GitHub](https://github.com/mrnugget/jev-shell-history)
- `jev-keyboard` (Rime IME reranking) [independent-with-code]: sends pinyin, candidates and up to 200 chars of preceding text (default 20); prefetches during input, applies on a Ctrl tap; default request wait 150 ms; warns users to stop the service before passwords; no accuracy figures — [GitHub](https://github.com/Ideny42/jev-keyboard)
- `jev-canvas` (voice + pointing -> tldraw) [independent-with-code]: Web Speech + MediaPipe fingertip; "mic -> state as text -> ONE Jev request -> policy -> editor.createShape(...)"; 9 questions (Nouls `is_command`, `complete`; Choices `action`, `shape`, `color`, `target`, `where`, `text_span`; Score `size`); thresholds `is_command` >= 0.5, `action` >= 0.55, `complete` >= 0.6, `where` >= 0.6; a placement command waits 900 ms after a pause unless `where` is clear; partial transcripts debounced 200 ms; at most 2 requests in flight, the older aborted; answers arriving after a newer applied one are dropped; pointer trail read back 300 ms (`SPEECH_LAG_MS`); "300 to 550 ms per decision" (tagline "~350 ms per spoken word"); ~1,900 tokens/request, ~$0.00008; 18/18 probe commands correct (10 English, 8 Ukrainian); Ukrainian imperatives scored `is_command` ~12% until the question named the language (then ~87%); a visible finger pulls `where` toward `point` so code honours `point` only when the transcript contains a pointing word — [GitHub](https://github.com/gaborishka/jev-canvas)
- `jev-voice-turn` (turn-end detection) [independent-with-code]: one request per partial transcript, at most one in flight, newest dispatched on return, stale answers discarded; state is `transcript_so_far`, `ms_since_last_word`, `word_count`, `assistant_state`, `assistant_is_saying`; fire at `turn_complete` >= 0.85 with >= 250 ms pause; below 0.35 the silence fallback stretches to 2,500 ms, else 1,000 ms; questions `turn_complete`, `intent` (8), `is_barge_in` (while speaking), `timer_duration`/`room`/`contact` only when regex finds spans; Jev p50 108 ms, p95 159 ms; fire delay ~260-280 ms after last word; mean assistant delay 351 ms vs 1,000 ms baseline (649 ms saved per turn); fired on 8/9 turns (miss scored 0.42-0.55); 58 requests/session, ~1.4 decisions/s while speaking; $0.0017/session (~697 tokens/decision); simulated microphone only — [GitHub](https://github.com/dabit3/jev-experiments/tree/main/jev-voice-turn)
- Catalogue: `TypeSafe Typewriter` ("16 typed judgments update live as you type", page is JS-only), `emoji-jev`, `jevmoji`, `jevseek` (Jev as token sampler), `Entune` dictation corrections, `jev-freeform` character-level chat — [awesome-jev README](https://raw.githubusercontent.com/hellogumbo/awesome-jev/main/README.md); [Typewriter demo](https://typesafe-demo.val.run/)

**Voice/home conversation agent (interface, not streaming)**
- `home-assistant-typesafe-conversation-agent` [independent-with-code]: one call per utterance with 8 fixed questions + 3 catalog-built + 1 per device kind + conditionals; an extra question "costs about 97 input tokens" vs ~250 ms for a second round trip; ~300 ms per call (sample `latency_ms: 244` at 6,482 tokens; ~$0.00027 per utterance for a 29-entity home); act only if confidence clears its band and the top-two margin >= 0.15: >= 0.75 act, 0.50-0.75 act and name the target, 0.30-0.50 ask which device, else sentence matcher -> LLM -> "I'm not sure"; confidence = `(n*p_top - 1)/(n - 1)` so "a two-option answer at p=0.66 scores 0.31, while a seven-option answer at the same probability scores 0.60"; `always_confirm_risky` on by default (unlock door, open garage, disarm alarm) "however sure the model is"; every question is speculative: "is everything locked up" returns `action_lock = lock` at 0.99 but the router treats it as a question ("A confident but wrong answer on a branch nobody reads is free"); Jev "cannot emit text, so it never invents a number": code finds candidate spans and Jev picks one — [GitHub](https://github.com/the-sof/home-assistant-typesafe-conversation-agent)

**In-browser re-creation**
- Shopify's Reflex [anecdotal/independent-with-code]: "System One model in your browser"; demo runs Qwen3.5-0.8B (~650 MB) on WebGPU, served configuration is 4B; `choice` up to 26 options; accepts text or an image as state; no millisecond timings published; the 4B Python package matches Jev on MMLU "within noise" per the author — [Reflex demo page](https://kshetrajna12.github.io/reflex/)

### Inferences
- The keystroke-rate projects converge on the same five mechanisms without coordinating: optimistic local result, one request per change, cancel-and-reject-stale, probability bands rather than argmax, and a code-owned score blend. Only judge-sheets (120 ms) and jev-canvas (200 ms) debounce; the launcher and shell-history rely on cancellation and accept paying for cancelled requests.
- Interface-selection latency is dominated by state size: ~100 ms at 1.4k tokens (launcher), ~120 ms at a few hundred (judge-sheets), 244-300 ms at 6.5k (HA agent), 300-550 ms at 1.9k plus speech (canvas). Workday's "instantly" is plausible at a few hundred milliseconds but is unmeasured publicly.
- Accessibility uses are indirect: AX-tree-driven agents (jev-ax-pilot, awlevin, mobile-jev) and voice control (canvas, HA agent, jev-voice) could serve as assistive input, but no project frames itself as an accessibility product or reports with disabled users.

### Gaps
- Workday discloses no component count, call frequency, latency distribution or fallback; the New Stack article is the only source and was fetched via a reader proxy.
- No adaptive-layout or form-field-prediction project with measured accuracy was found beyond judge-sheets' hand-checked columns.
- Nader Dabit's "predictive spreadsheet ~100 ms" social claim maps to judge-sheets (72-132 ms header chip), but the "keystroke oracle" X post itself was not fetched; the repo README is the source used.

## KQ5. Streaming and event processing: logs, alerts, chat moderation, home automation, IoT

### Takeaway
Streaming uses run Jev per event with 4-7 questions fanned out in one request and 8-96 requests in flight, reaching ~190-300 judged events/s per API key before 429s; the cost model is linear in tokens (jev-firehose: 835 tokens/msg = $37.86/hour at 300 msg/s). Windowed batching is used for incident grouping (60 s by `service:category`) and for merging related events (jevbus 5 s windows), not for the judgment itself; one project measured per-request batching of 8 events as 8x throughput at the same ~110 ms p50. Fallback under load is a regex/heuristic path with explicit shedding thresholds. Home automation is request-driven, not streaming: TypeSafe's smart-home demo and HA-Jev answer per utterance or per automation trigger.

### Inferences
- Per-event vs per-window: all moderation/triage projects judge per event (or per small batch of consecutive events) and use time windows only downstream for grouping and dedup. The one direct measurement (log-sentinel) shows batching 8 events per request multiplies throughput per connection ~8x at unchanged p50, which is the main lever for staying under the request-rate limit.
- The throughput wall is the API key's rate limit (~300 msg/s in firehose; 429s above ~200 lines/s at concurrency 16 in log-sentinel), consistent with the third-party-reported 1,200 requests/min account limit (KQ6). Above the wall, p95 degrades from ~370 ms to seconds within 20 s, so streaming engines need explicit load shedding to a heuristic, which both dabit3 demos implement.
- Home automation is the clearest case of request-driven speculative fan-out (TypeSafe demo, HA agent): the cost of an extra question (~97 tokens) is far below a second round trip (~250 ms), so every plausible branch is asked and code discards answers.

## KQ6. Latency engineering: caching, speculative pre-asking, concurrency, regional, gateway vs direct

### Takeaway
Hosted Jev's observed floor in loops is ~80-125 ms p50 at 1-2k input tokens over a warm direct connection, rising with tokens (~220 ms at 4k, ~245-335 ms at 6.5k) and with p95 2-3x p50; TLS setup adds ~500 ms on the first call. Nobody reports a regional measurement; one README says p50 "depends on distance to api.typesafe.ai", and Hao's self-hosted loop fell from ~330 ms to ~24 ms by colocating. The practised levers are: fan-out (ask everything in one request), speculative heads, client-side caching keyed on exact (state, question) or a state fingerprint, re-ask only on state change, concurrency to cut decision age at constant per-call latency, and server prefix caching (open models only).

### Cited Findings
- Vendor figures: end-to-end "70ms-500ms"; "40x-200x faster" on System One queries — [TypeSafe launch post](https://typesafe.ai/blog/introducing-system-one-models-and-jev). Fan-out: "All questions are evaluated in parallel, so adding more questions usually has little effect on response time"; speculative questions "save a round trip" — [TypeSafe fan-out pattern](https://docs.typesafe.ai/patterns/fan-out). Limits are "measured in tokens per second and requests per second", shown only in the console; 429 on breach; SDKs retry honouring `retry-after`; "Jev ingests `state` once and evaluates all questions against it in parallel"; no caching guidance; the models page still lists text-only input — [TypeSafe models page](https://docs.typesafe.ai/models)
- Third-party limits summary (page read 18 Sep): 250,000 input tokens/s and 1,200 requests/min per account ("about 20 per second sustained"), "adjusting dynamically"; the two caps cross at 12,500 tokens/request; SDK default timeout 10.0 s; no regions stated — [opentweet.io](https://opentweet.io/jev/limits). An earlier summary gave 100,000 tokens/s and 40 requests/s; the sources conflict — [innfactory summary](https://innfactory.ai/en/ai-models/typesafe-jev/)
- Independent latency claims are thin: Guillermo Rauch's "up to 18x faster (p95)" on a live safety-review step has no absolute numbers; the eesel "tested" article describes no test of its own — [eesel.ai](https://www.eesel.ai/blog/jev-ultrafast)
- Measured p50/p95 in loops (direct API unless noted): jev-ax-pilot p50 82-126 ms, p95 138-351 ms at ~2k tokens; jev-launcher p50 ~100 ms, p95 ~200-300 ms at ~1.4k tokens, first request ~500 ms (TLS), "p50 depends on distance to `api.typesafe.ai`"; judge-sheets p50 114-120 ms, p95 259-379 ms; jev-voice-turn p50 108 ms, p95 159 ms at ~700 tokens; log-sentinel p50 ~100-120 ms, p95 ~250-360 ms, p99 ~370-540 ms; jev-firehose p50 122 ms, p95 366 ms at 835 tokens; jev-drone 0.110-0.118 s median, 0.164 s p90; clash-jev ~135 ms; pick-and-place 146 ms median; jevscape 0.22 s median, 0.31 s p90 at ~3,950 tokens; HA agent 244 ms at 6,482 tokens; jev-state p50 335 ms, p95 390-422 ms at 700-1,236 tokens; ping-pong 325 ms median, 889 ms max; pong-jev 379 ms per call at ~520 tokens; jev-grand-prix ~270 ms; jev-ui-test 458 ms median, 919 ms p90; shell-history 0.7-0.9 s — sources as cited in KQ1-KQ5
- Gateway paths: OpenRouter Banking77 median 175 ms — [The New Stack](https://r.jina.ai/https://thenewstack.io/workday-is-using-typesafes-jev-to-build-user-interfaces-on-the-fly/); teknium1 via OpenRouter `/api/alpha/decisions` 211-227 ms median — [GitHub](https://github.com/teknium1/hermes-and-jev-play-minecraft); jev-canvas via OpenRouter 300-550 ms — [GitHub](https://github.com/gaborishka/jev-canvas); Pokémon via Vercel AI Gateway median 621 ms (n=6) — [GitHub](https://github.com/valentynkit/jev-plays-pokemon-red)
- Concurrency to cut decision age: pong-jev concurrency 1 -> 3 cut decision age 196 -> 111 ms while per-call latency stayed 379 ms, and drops out-of-order replies by sequence number — [GitHub](https://github.com/safzanpirani/pong-jev); jev-drone sequential ceiling 7.4 Hz vs 21 decisions/s pipelined with 4-6 workers — [GitHub](https://github.com/RomanSlack/jev-drone); judge-sheets 12-lane pool; log-sentinel concurrency 8 (~190/s) with 429s at 16; firehose 96 in flight — as cited
- Client-side caching of identical states: judge-sheets caches by (kind, text, instructions, options) ("zero requests" on retry) — [GitHub](https://github.com/dabit3/jev-experiments/tree/main/judge-sheets); jev-drone "reuses the last judgment when the scene fingerprint is unchanged" and skips calls on an open corridor — [GitHub](https://github.com/RomanSlack/jev-drone); jev-realtime-trading re-asks only after a 0.02% price move or 10 s — [GitHub](https://github.com/rthomas24/jev-realtime-trading); jevbus 24 h TTL / 10k LRU — [GitHub](https://github.com/zkjoie/jevbus); JevLight skips empty junctions — [GitHub](https://github.com/usail-hkust/JevLight); DSPy applies thresholds locally "so identical requests reuse cached evidence" (captured 2026-10-15 by the earlier researcher) — [DSPy 3.4.0 notes](https://newreleases.io/project/github/stanfordnlp/dspy/release/3.4.0)
- Speculative pre-asking in loops: operation + all target heads (jev-ultrafast, mobile-jev, jev-ui-test); smart-home's four-question batch; HA agent's 12+ questions per utterance (97 tokens vs 250 ms per extra round trip); Instinct's bundled call 1; JevLight's congestion Noul; jev-launcher's `match_cN` per candidate — as cited. No project pre-asks about predicted *next* states; the nearest is pong-jev's `--aim`, which extrapolates the ball and asks about the arrival point — [GitHub](https://github.com/safzanpirani/pong-jev)
- Server-side prefix caching (open models only): Blocks.ai 1,017 ms -> 133 ms after prefix KV caching — [Blocks.ai](https://blocks.ai/blog/jev-open-model-doom); Hao: ~6 ms fixed + ~10.4 ms per 1,000 uncached tokens, only ~480/1,760 tokens cached, "Prompt layout strongly affects cache hits", laptop tunnel ~330 ms vs colocated ~24 ms — [Hao AI Lab blog](https://haoailab.com/blogs/mcjev/)
- Decision cadence guidance [anecdotal/vendor-adjacent]: "There is no universal cadence"; "Calling a decision service every rendered frame adds latency and jitter"; "Every request needs a deadline"; if late "keep the current intent, move to cover, run an authored behavior tree, or hold position"; track "State version and stale-result rate" — [Seeles guide, 21 Sep](https://www.seeles.ai/resources/blogs/jev-games)

### Inferences
- Across hosted loops, p50 scales roughly linearly with input tokens (~100 ms at 1-2k, ~220 ms at 4k, ~250-335 ms at 6.5k), so state pre-digestion (jev-state's -43% tokens) is a latency lever as well as an accuracy one. The outliers (pong-jev 379 ms at 520 tokens, Pokémon 621 ms) run through gateways or unknown regions, suggesting routing adds 100-400 ms.
- Gateways (OpenRouter, Vercel AI Gateway) cost roughly +75-500 ms over direct in these samples; no author quantified it head-to-head.
- Nobody caches on the server for hosted Jev because the API exposes no cache control; all caching is client-side and exact-match or fingerprint-based, which only pays off when states repeat (spreadsheet retries, calm tape, open corridor). For continuous control the win came from skipping calls on quiet states, not from hits.

### Gaps
- No regional latency table exists for api.typesafe.ai; no author compared US vs EU or gateway vs direct on the same requests.
- TypeSafe's "13 questions ~12x cheaper, ~10x faster" fan-out figures referenced by third parties are not on the current fan-out page.
- No published rate-limit numbers from TypeSafe itself; third-party figures conflict (40 rps vs 20 rps sustained).

## KQ8. Failure reports: oscillation, stale decisions, overconfident wrong actions, cost blow-ups, mitigations

### Takeaway
The reported loop failures are mostly harness-level: oscillation from re-deciding every tick (Blocks.ai target flipping, grand-prix weaving, Doom heading changes), stale state producing confidently wrong actions (pong "stay" while the ball climbed; jev-drone's 152/182 queued requests), menus that let Jev keep choosing a satisfied or null action (teknium1 `mine_dirt`/`wait`), option wording that pins a Choice (grand-prix "normal"/"maximum"), and rate-limit collapse under load (firehose 400 msg/s). Mitigations adopted: split control so code owns continuous actuation and Jev picks discrete targets at low rate, re-decide only on state change, drop late answers, shrink and rename menus, band numbers, and shed to heuristics with explicit labels. Cost blow-ups were not reported; the highest hourly figures are $37.86/h (300 msg/s moderation) and $7/h (10 Hz Doom).

### Cited Findings
- Oscillation / orbiting / stuck (open-model Doom): "switching targets every tick made the agent flip between two flanking monsters"; an inverted bearing sign made it circle; a 700-unit shooting threshold produced 229 shots and no kills; asking for an open direction every tick caused constant heading changes, and a BFS walkability grid cut stuck decisions on E1M1 from ~33 to 3 — [Blocks.ai](https://blocks.ai/blog/jev-open-model-doom)
- Weaving from direct continuous control: Jev steering directly gave DNF with 9 off-tracks and 1 crash; choosing line and pedals while code steers at 120 Hz gave 0 off-tracks; overlapping option descriptions made it always pick "normal"; a level named "maximum" was read literally — [jev-grand-prix](https://github.com/enoyola/jev-grand-prix)
- Stale decisions: "the sim-time pacing bug meant 152 of 182 requests hit a full queue, so the model influenced nothing" — [jev-drone](https://github.com/RomanSlack/jev-drone); "Without `--aim`, stale ball state made Jev say 'stay' when the ball was climbing toward the paddle, losing the point"; frameskip 4 makes even a perfect tracker lose 1-21 — [pong-jev](https://github.com/safzanpirani/pong-jev); a frame is ~350 ms old when read and three sequential requests plus a tap add ~560 ms — [clash-jev](https://github.com/bytelabs-oss/clash-jev)

- Overconfidence and calibration quirks: with the nuts Jev shoved 62% where the solver checked 100% (captured 2026-10-15) — [backnotprop](https://backnotprop.com/blog/jev-poker/); confidence `(n*p_top-1)/(n-1)` scores the same probability differently by option count — [HA agent](https://github.com/the-sof/home-assistant-typesafe-conversation-agent); pong confidence 0.25-0.55 in ambiguous frames, `--min-confidence` "has not been swept" — [pong-jev](https://github.com/safzanpirani/pong-jev); Vipul's agent "broke off mid-fight as its odds turned" (presented as a feature) — [eChai](https://echai.ventures/feed/i-hooked-up-jev-by-typesafeai-to-a-few-agents-on-my-minecraft-world-614)
- Load and transport: at 400 msg/s 2,351 HTTP 429 retries in 20 s, 224 hard failures, e2e p95 4.0 s, 12.6% shed to heuristics — [jev-firehose](https://github.com/dabit3/jev-experiments/tree/main/jev-firehose); 300 lines/s grows backlog to p95 ~750 ms — [log-sentinel](https://github.com/dabit3/jev-experiments/tree/main/log-sentinel); 113 transport errors and 38 HTTP 402 account blocks in one study — [RoboJEV](https://github.com/lykycy123/RoboJEV); "Canceled requests may still be billed server-side" — [jev-launcher](https://github.com/dabit3/jev-experiments/tree/main/jev-launcher); one 429 handled by a deterministic heuristic that then pressed "Dark" twice — [jev-ax-pilot](https://github.com/dabit3/jev-experiments/tree/main/jev-ax-pilot)
- Harness-does-the-work critique: "the harness is doing a _ton_ of heavy lifting"; "99% of the work"; a tester without the harness said Jev "was not able to even get to Professor Oak's lab" — [Pokémon HN thread](https://news.ycombinator.com/item?id=49845172); "You can build a harness where a coin flip is playing Doom" — [HN Algolia](https://hn.algolia.com/api/v1/search?query=jev%20doom&hitsPerPage=20); jevscape author asks that Jev "always be shown beside the random baseline" — [jevscape](https://github.com/Skyvern-AI/jevscape)
- Vendor-acknowledged weaknesses relevant in loops: "`jev-1.13` leans toward the option that comes first"; "Jev is not a calculator"; "does not count reliably"; dates "unreliable" for ordering and windows; RGB/hex closeness unreliable — [TypeSafe jaggedness docs](https://docs.typesafe.ai/model-jaggedness/jev-1.13)
- Self-hosted model weaknesses: v9 prompt still lost 12/14 to a scripted archer; Sumo mode lost 88% to humans; NVFP4 ~9% slower than BF16 at their batch size — [Hao AI Lab blog](https://haoailab.com/blogs/mcjev/)
- Mitigations in code (handling numbers/dates/position bias inside loops): band HP and distances into labels, prune to nearest five (jev-state); digit-free relative phrases (pong-jev); code computes pot odds/SPR (poker), `jump_must_start_this_decision` (mario), dates and offsets (awlevin), "code-evaluated arithmetic facts" (jev-ax-pilot), "plain facts because the model ... isn't good at comparing" numbers (jev-realtime-trading); Jev picks a span rather than emitting a number (HA agent, mobile-jev); only two projects address order: Instinct's beam over top-2 families and the AnyJev library's cyclic rotations (not Jev) — [AnyJev order-bias post](https://wavect.io/blog/anyjev-calibration-option-order-bias/)

### Inferences
- The recurring root cause of oscillation is re-deciding a continuous quantity every tick with no memory; every fix converted Jev's output into a discrete target held by code (line/pedal, waypoint, intent for 0.5 s) or added a hold rule (two consecutive checks, 45 s minimum hold, "keep CURRENT" as the first option).
- Stale answers are handled by sequence numbers and buffer/fingerprint equality checks in interface loops, and by "keep current action" in control loops; no project reports a stale-rate metric, though Seeles recommends one.
- No cost blow-up was reported because every loop caps spend ($5 budgets, 60-action limits, call-count refusals) or runs at under ~10 Hz; the cost risk is concentrated in verbose states (28k tokens/decision in the drone swarm) rather than tick rate.

### Gaps
- No reported incident of an overconfident wrong action causing real-world harm; all failures are in simulators, games or paper trading.
- No one measured position bias inside a loop (e.g. by rotating element tables); the first-option lean is documented by TypeSafe but unquantified in practice.
- Hao's and TypeSafe's own demos publish no failure statistics (deaths, stuck rate, late decisions).

## KQ9. What a generic decision engine must offer to support the reflex/sensor pattern

### Takeaway
The projects above re-implement the same nine facilities by hand; an engine that provides them as configuration would cover every loop found: tick scheduling with model-chosen re-poll intervals, deadline-plus-stale handling (sequence numbers, state fingerprints, keep-current default), speculative fan-out with code-side discard, exact-match and fingerprint caching with change-triggered re-ask, debouncing for human input, hysteresis bands and minimum hold times for actions, code-owned safety floors that withhold options and override on reflex, labelled heuristic fallback with load shedding, and per-decision telemetry (latency, decision age, stale rate, cost) alongside a mandatory random/rules baseline.

### Cited Findings (evidence for each requirement)
- **Tick scheduling, including model-chosen cadence:** jevscape's `poll_again_in_ticks` answer picks N, 2N, 5 or 10 ticks and "The answer timeout equals the poll interval" — [jevscape](https://github.com/Skyvern-AI/jevscape); jev-drone's 500/50/15/2.5 Hz layering — [jev-drone](https://github.com/RomanSlack/jev-drone); grand-prix 120 Hz steer vs 3.5 Hz Jev — [jev-grand-prix](https://github.com/enoyola/jev-grand-prix); Hao's 50 ms body vs ~6 Hz head — [Hao AI Lab](https://haoailab.com/blogs/mcjev/); DoomSat 0.5 s intents — [DoomSat](https://github.com/doom-satellite/DoomSat); Seeles: "There is no universal cadence" — [Seeles](https://www.seeles.ai/resources/blogs/jev-games)
- **Deadline and stale-answer handling:** "A late answer keeps the current action" — [jevscape](https://github.com/Skyvern-AI/jevscape); late -> `hold` with `decision.late: true` — [jev-trader](https://github.com/jarrodwatts/jev-trader); "Superseded requests are canceled, and late responses are rejected" — [jev-launcher](https://github.com/dabit3/jev-experiments/tree/main/jev-launcher); apply only if "the buffer is still what was typed when the request started" — [jev-shell-history](https://github.com/mrnugget/jev-shell-history); "An answer arriving after a newer one has already been applied is dropped" — [jev-canvas](https://github.com/gaborishka/jev-canvas); out-of-order replies dropped by sequence number — [pong-jev](https://github.com/safzanpirani/pong-jev); keep previous phase on failure/low confidence — [JevLight](https://github.com/usail-hkust/JevLight); "Every request needs a deadline" — [Seeles](https://www.seeles.ai/resources/blogs/jev-games)

- **Telemetry and baselines:** decision age vs per-call latency tables — [pong-jev](https://github.com/safzanpirani/pong-jev); "State version and stale-result rate" — [Seeles](https://www.seeles.ai/resources/blogs/jev-games); 0 late actions logged — [ping-pong](https://github.com/Icohen007/jev-play-ping-pong); "always be shown beside the random baseline" — [jevscape](https://github.com/Skyvern-AI/jevscape); rules controller identical to Jev — [pick-and-place](https://github.com/tryaksh/jev-pick-and-place-study)

### Inferences
- An engine's tick scheduler should accept the model's own re-poll suggestion as a hint but clamp it in code (jevscape pattern), and should treat "no state change since last answer" as a free tick (jev-drone, realtime-trading).
- Stale handling needs two keys: a monotonic sequence per request and a state fingerprint; interface loops need the fingerprint (reject if the input changed), control loops need the sequence (drop out-of-order) plus a default action for late ticks.
- Because Jev confidence is a function of the distribution and option count, hysteresis should be defined on the chosen option's probability and the top-two margin (as the HA agent does), not on the confidence field.
- The "harness carries the knowledge" critique is itself a requirement: the engine should ship a random/rules/first-option baseline runner so that any reported gain is relative, which three authors already do voluntarily.

### Gaps
- No project implements speculative pre-asking about predicted next states (ask now about the state expected after the current action lands); pong-jev's `--aim` is the only partial case.
- No engine-level library found that packages these facilities for Jev; jevbus (event routing) and jev-state (state banding) each cover one slice.
